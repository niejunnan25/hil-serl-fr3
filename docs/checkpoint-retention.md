# 每轮保留五个 checkpoint

项目配置 `checkpoint_keep=5` 是当前存储策略。新建训练与之后显式续训的 attempt 都使用它；旧 run 的模型、输入、数据和安全配置保持原快照，原 run.json/config.json 不重写。值为 0 可关闭自动清理。

五个名额内按以下顺序保留：

1. 最新的完整 checkpoint，用于恢复模型、优化器、目标网络和 RNG。
2. 正在评估读取的 checkpoint（如与最新不同，占另一个名额）。
3. 同条件独立评估中成功率最高的版本；成功率相同时优先较新 step。
4. 没有评估成绩的空余名额，按 step 从新到旧补齐。

因此一般是“最新恢复点 + 最优四个”，没有评估数据时就是最新五个。这里没有把“最新”误称为“效果最好”。少于五份的训练组全部保留；不跨 run 比较或合并。

## 评估如何计分

仅接受控制台独立 eval 的至少 10 条完整轨迹，全部无软件接管、步骤数大于零、每条具有人工最终 0/1 结果，且完成了本次要求的全部条数。训练期间的接管后成功率、未完成的 eval 和少于十条的快速测试不参与排名，也不伪造为零分。

eval reset 随机序列由 seed 和已完成的 case 序号固定。失败或中断重试不前移 case。比较条件包括评估条数、seed、环境/观测/安全与判定配置及实际源码指纹；仅在最近的同条件评估簇内比较。这里的同条件是软件可记录的条件，操作者仍需保证实际场景布置一致。

评估证据存放在 eval run 的 `evaluation.json` 和模型目录的 `retention_scores.json`。保留原始评估轨迹；后者以 step 为键指向经校验的证据。重复提交同次评估幂等；缺失、篡改或非法成绩不参与排序。评分模块不运行机器人、不生成虚构评估。

## 保存、读取与删除边界

先完整写入新模型并确认 commit，再独立执行清理。清理失败会保留已保存模型并记录 `retention_status.json` 的错误，不把它说成“checkpoint 没保存”。下一次保存会再次执行保留策略；磁盘/权限错误时可能暂时超过五份，错误可由 status 和日志查看。

评估启动前取得模型专用共享读锁，通过继承文件描述符保护整个初始化和评估过程。清理持另一把短期计划锁，探测正在使用的模型并把它放进上述五个名额，而不是让 Learner 等待整个评估。若使用中的模型数量超过预算则明确延后清理。

只选择规范名称 `checkpoint_<非负整数>` 且已提交的文件/Orbax目录。临时、未提交、符号链接以及未支持的旧 `_gda` 分片对会被保留。检查模型清单发生变化时停止删除。保留/删除的具体路径、大小和完成结果写入 `retention.jsonl`。

训练回放 buffer、demo_buffer、原始 NPZ、视频、帧索引、示范和 classifier checkpoint 不属于清理范围。输入继续使用已选定的 160×160 ROI profile。
